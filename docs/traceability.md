# Traceability Matrix

This document defines the schema, the status vocabulary and the rules, and holds the matrix that connects each requirement to its implementation, test, evidence and status. Process is in [sdd.md](sdd.md).

## 1. Notes on this matrix

- **Phase 1 is owner-declared closed** (SDD-D-1 in [decisions.md](decisions.md)). That is a delivery-status decision. No Phase 1 requirement is `Verified` merely because the phase is closed.
- **Eleven Phase 0 requirements are `Verified`** from dated 2026-11-20 local runs: CORE-AC-2, CORE-AC-4, DBM-INV-3, DBM-AC-1, DBM-AC-3, API-AC-1, OUT-INV-1 and OBS-INV-1 ([T-002](tasks/T-002-phase0-reverification.md#evidence)); JOB-AC-2, OUT-AC-3 and OUT-AC-2 ([T-015](tasks/T-015-real-redis-queue-outbox-tests.md#evidence)). AC-63 is `Verified` ([T-019](reports/2026-11-21-T-019-instructions-version.md), 2026-11-21) and ten AI Platform `run` criteria are `Verified` from [T-011](tasks/T-011-ai-platform-sync-run-path.md#evidence) (2026-11-24, spec-auditor PASS): AC-15, AC-17, AC-18, AC-19 and AC-22 to AC-27. AC-29 and AC-59 are `Verified` on the `run` path from [T-023](tasks/T-023-ai-platform-run-followups.md#evidence) (2026-11-24 run, spec-auditor PASS 2026-11-25). No other requirement is `Verified`. The Phase 0 report dated 2026-10-14 is cited as historical evidence on the rows it covers and is not accepted as current evidence.
- **Mappings come from reading source and test code**, not from file names or from IDs cited in comments. Many mappings are partial; the Notes column says which part a test covers. A mapped test is not a claim that it passes.
- **Status used here.** `Implemented`: an implementation is identified (tests may or may not be mapped, none executed). `Specified`: the spec exists and no implementation exists yet (AI Platform work not yet built). `Gap`: no test is mapped, or the implementation could not be identified. `Blocked`: a named authorization prevents verification.
- **Not covered here.** web_foundation has no spec in this repository (T-007). Modules without a spec have no rows. Frontend sections of the specs carry no IDs (T-010).
- Rows reference the `app/` and `tests/` paths as inspected; an unavailable or uninspected reference is stated as `unmapped`.

## 2. Schema

| Field | Meaning |
| --- | --- |
| Requirement ID | Stable AC or INV identifier, exactly as written in the source spec (`<MODULE>-INV-n`, `<MODULE>-AC-n`; AI Platform `INV-n`, `AC-n`) |
| Module | Owning module (names as in [modules.md](modules.md)) |
| Spec | Source specification file |
| Spec section | Exact section containing the requirement |
| Implementation | Relevant source file or symbol |
| Test | Relevant test file and test name |
| Evidence | Dated test execution or report reference |
| Status | One of Specified, Implemented, Verified, Gap, Blocked |
| Notes | Missing evidence, limitations or explanation |

## 3. Status definitions

| Status | Meaning | Minimum required to use it |
| --- | --- | --- |
| Specified | The requirement exists in an approved or draft spec. No implementation is claimed. | Spec and spec section filled |
| Implemented | Implementation exists and is identified. No passing test run is claimed. | Implementation reference filled |
| Verified | A mapped test or demonstrated workflow was executed and passed, and the result is recorded with a date. | Test and Evidence both filled, and Evidence includes the execution date |
| Gap | The requirement is not met, not mapped, or the evidence is missing or unsatisfactory, and no blocker is known. | Notes state what is missing |
| Blocked | Verification or implementation cannot proceed until a named dependency is resolved. | Notes name the blocker |

## 4. Rules

1. **Verified requires dated execution evidence.** Evidence must be a recorded test run or verification report with a date. A requirement without that evidence cannot be `Verified`.
2. A test file existing is not proof that a test passed.
3. A count of test functions is not proof of conformance to a requirement.
4. A passing run on a different environment than the one the requirement names does not count. For example, local PostgreSQL does not verify a criterion that names a Neon TEST branch (SDD-D-2).
5. A missing mapping stays explicitly **unmapped**. Write `unmapped` in the cell. Do not leave it blank and do not guess.
6. Do not fill Implementation or Test with speculative references. Only record references that were inspected.
7. Preserve the AC and INV identifiers used in the source specs. Do not renumber them.
8. If a spec has no stable ID for a requirement, record that as a note. IDs are assigned and kept stable under SDD-D-5; never reuse or renumber one.
9. Evidence must not be invented, back-dated or copied from a different run. A report dated earlier cannot verify behavior that changed afterwards.
10. Closing a phase does not change a requirement's status.
11. Status changes are reviewed by the owner at milestone level.
